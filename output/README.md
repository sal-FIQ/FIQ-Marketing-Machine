# Output Directory

The `output` folder holds the **deliverables generated by your skills**—the final work products you publish or share with stakeholders: diagnostics, strategies, blog posts, social updates, email sequences, landing pages, ad copy, supporting apps, and more.

This directory is deliberately kept separate from the rest of the repository:

| Zone | Folders | Purpose |
|---|---|---|
| **The machine** | `foundation/`, `prompts/`, `skills/` | Reusable system that *produces* work |
| **Source material** | `research/` | Raw inputs that *inform* the machine |
| **Output** | `output/` (this folder) | Generated deliverables — *the result* |

Skills **read from** `foundation/` and `research/` and **write to** `output/`. Nothing generated should land back in the machine or research folders.

## Organizing Outputs

Group deliverables in **one subfolder per engagement** — a client, campaign, or project. Each engagement folder is self-contained, so it's easy to share, version, or hand off.

```
output/
├─ urban-district-developments/        # an engagement
│  ├─ marketing-diagnostic.md          # the primary deliverable
│  └─ app/                             # supporting assets (e.g. a deployable web app)
│     ├─ index.html
│     └─ README.md
└─ <next-engagement>/
   ├─ blog-posts/
   ├─ email-campaigns/
   └─ ...
```

Within an engagement, organize by type or date as needed (e.g. `blog-posts/`, `email-campaigns/`, `2026-05-launch/`).

## Best Practices

* Name each engagement folder clearly (client or project name, kebab-case).
* Include metadata such as creation date, author, and context where relevant.
* Store only final or near-final drafts here; use the `research/` folder for messy notes and early iterations.
* If a deliverable was produced from a specific skill and set of foundation files, note that at the top of the file for traceability.
